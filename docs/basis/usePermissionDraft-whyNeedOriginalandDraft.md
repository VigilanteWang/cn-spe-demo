如果在草稿编辑期间，后端的真实数据发生了改变，系统的交互逻辑和数据流转会变得更加复杂。以下是为什么必须保留 `original` 以及不能直接用 `draft` 对比后端的深层原因：

#### 1. 意图丢失与“幽灵覆盖” (Lost Intent & Phantom Overwrites)

假设我们不保留 `original`，只对比 `draft` 和后端真实值，会面临灾难性的逻辑缺陷。我们可以通过一个“三向合并（3-Way Merge）”的场景来说明：

- **T0时刻**：后端数据是 `A`。用户打开弹窗，此时 `draft` 为 `A`。
- **T1时刻**：后端数据被另一个管理员改成了 `B`。
- **T2时刻**：当前用户在前端将 `draft` 从 `A` 改成了 `C`。
- **T3时刻（提交）**：如果此时我们拿 `draft` (C) 直接去和后端的真实值 (B) 对比。系统发现它们不同。

**问题来了：** 系统如何知道这个“不同”是怎么产生的？
前端是想把 `B` 改成 `C`，还是想把 `A` 改成 `C`？如果直接将 `C` 写入后端，那么另一个管理员在 T1 时刻所做的修改 `B` 就会被无声无息地覆盖掉（这被称为“丢失的更新”或“幽灵覆盖”）。

**有 `original` 时的正确解法：**
因为有 `original` (A) 的存在，系统在提交时会进行对比：

- **检测冲突**：系统发现 `original` (A) $\neq$ 后端真实值 (B)。立刻知道发生了并发修改冲突！
- **安全拦截**：系统可以拒绝提交，并提示用户：“该数据已被他人修改，请刷新后重试”。

#### 2. 乐观并发控制的基础 (Optimistic Concurrency Control)

在真实的后端交互中，`original` 往往不仅仅包含业务数据，还包含一个关键的**版本号（Version）**或 **ETag**。

- 当执行 `applyDraft` 向后端发起请求时，前端会将 `draft` 数据连同 `original` 的版本号一起发送。
- 后端收到请求后，会将传入的 `original` 版本号与数据库中当前的版本号进行对比。
- 如果匹配，说明期间无人修改，后端执行更新。如果不匹配，返回 `HTTP 409 Conflict`。
- 这种机制使得前端不需要一直持有数据库的锁，极大地提升了系统性能，而 `original` 就是这个机制在前端的载体。

#### 3. 前端同步 UI 渲染的强制要求 (Synchronous UI Rendering)

从纯前端交互的角度来看，判断 `hasUnsavedChanges`（是否有未保存的更改）必须是一个**同步（Synchronous）且极其廉价**的操作。

- 只要用户在界面上敲击键盘或点击鼠标，前端就需要立刻知道草稿是否发生了变化，以此来决定是否点亮“保存”按钮。如果每次网络请求，会卡顿

还有一个更细节的场景：如果不使用 original，判断公式只能是 draft !== initial。

当用户点击保存，调用后台接口并返回成功时，此时的 draft 已经是最新状态，但父组件的 initial 还是旧的（因为父组件需要发起新的网络请求去拉取最新数据，这需要时间）。

在这个“时间差”内，draft !== initial 依然成立。这将导致界面上的“保存”按钮无法立刻置灰，或者用户此时尝试关闭弹窗，系统依然会错误地拦截并警告“有未保存的修改”。

#### 4. Close/Reset 正确语义

用户期待点击 Reset 时，表单能够回到打开弹窗时的状态（即 original），而不是后端最新的状态（initial）。如果没有 original，用户点击 Reset 后会发现表单数据突然跳变到后端最新状态，这种就不符合语义预期了。
